2El sistema de un vistazo

La idea rectora del repositorio: un solo núcleo científico en Python que corre en dos runtimes. El mismo código —el mismo wheel, de hecho— se ejecuta en el servidor FastAPI y dentro del navegador vía Pyodide. El frontend no sabe cuál está usando.

Hasta agosto de 2026 ésta era la sección peligrosa del repositorio: siete piezas de lógica duplicadas a mano entre los dos lenguajes, cinco de ellas sin ninguna red. La cirugía de arquitectura las atacó una por una. Vale la pena conservar el registro de qué era cada una, porque explica por qué el código está como está.

Regla de decisión: se duplica sólo lo que la UI necesita antes de tener un resultado del motor, y todo lo duplicado va pineado con un golden. Todo lo demás se calcula en Python y viaja serializado. Quedan exactamente dos espejos, los dos por la misma razón —la UI los necesita antes de tener resultado— y los dos pineados. Ninguna otra forma se escribe dos veces.

Las cinco trampas que ya mordieron

  1. El wheel viejo. Tras tocar el núcleo hay que correr npm run sync:core --workspace @titirilquen/web o Pyodide sigue ejecutando el código anterior. No lo hace el dev, ni el build, ni Vercel. El wheel va versionado en git justamente por eso.
  2. Presets con valores absolutos. Declaran valores, no diferencias: al recalibrar un default hay que moverlos, o aplicar una política revierte ese parámetro en silencio. Ya pasó cuatro veces; la quinta fue factor_flota, que faltaba en 6 de las 8 políticas.
  3. Una tercera copia de los betas vivía en un script de auditoría y midió valores viejos sin avisar. Eliminada, pero el patrón vuelve.
  4. model_copy(update=…) de Pydantic no valida: una clave inexistente se cuela como atributo suelto y el barrido reporta «inerte» un parámetro que no se está moviendo. Los scripts llevan un guard.
  5. Sub-objetos anidados. Cualquier recorrido de la configuración que asuma estructura plana se salta penalizaciones_fisicas en silencio. Produjo una falsa anomalía en la auditoría del todo-o-nada.

Dos cosas que ningún test de acá detecta. Los 105 tests del núcleo corren en CPython, no en Pyodide: subir el piso de pydantic a >=2.8 dejó el motor por defecto sin arrancar —Pyodide 0.26.4 trae 2.7.0 precompilado y micropip aborta— con la suite entera en verde. Y varias claves de i18n se construyen por interpolación (t(`equilibrium.modo_${m}`)), así que un grep de la clave literal da cero y miente: borrar una familia «huérfana» dejó los botones mostrando claves crudas.

extra="forbid". Agregar un campo nuevo con default es seguro; quitar o renombrar uno rompe la importación de escenarios .ttrq.json ya guardados y los enlaces ?s=. En agosto de 2026 eso se hizo a propósito: se borraron cinco campos muertos y el método pasó de "wardrop" a "todo_o_nada". El $schema subió a v3 y no hay migraciones — un archivo anterior falla con un error explícito, que es mejor que abrirse con valores adivinados.

Verificación completa antes de un commit

# Si tocaste el núcleo, esto PRIMERO: recompila el wheel, regenera el
# contrato TypeScript y los goldens. Nadie más lo hace por vos.
npm run sync:core --workspace @titirilquen/web

cd packages/titirilquen_core && uv run --extra dev pytest        # 105 tests + línea base
cd apps/web && npm run typecheck && npm run test:e2e:fast        # tipos + 58 e2e
npm run format:check                                              # desde la raíz

Lo que ningún comando de acá comprueba: que el navegador siga funcionando. El motor por defecto corre en Pyodide, donde no hay tests. Tras un cambio en el núcleo o en la frontera, abrir la app y correr una simulación es parte de la verificación, no un lujo.
